# backend-architecture-lab

Стенд курса **«Архитектура бэкенда: распределённые системы и системный
дизайн»**. Здесь распределённую систему можно потрогать руками: запустить
сцену одной командой и увидеть, как отказ, который курс обсуждает словами,
случается на самом деле.

Курс утверждает — стенд показывает. Всё, что можно воспроизвести,
воспроизводится здесь; числа в тексте шагов берутся из вывода этих сцен, а не
пишутся по памяти.

## Быстрый старт

Нужен только **Docker** (Desktop на macOS/Windows, engine на Linux). Ни make,
ни языковых рантаймов, ни установки пакетов.

```bash
git clone https://github.com/kipyatl0/backend-architecture-lab.git
cd backend-architecture-lab
./lab scene 1
```

Сцена сама поднимет нужный профиль и сама вернёт данные в исходное состояние.
Первый запуск дольше: тянутся образы. Дальше — около сорока секунд, столько
сцена и длится.

```
Сцена 1 · m01 l04 · профиль mono · детерминирована
Провайдер отвечает 30 с, клиент повторяет
Подготовка: состояние сброшено, следующий заказ 7714, эквайринг отвечает через 30s
Клиент ждёт ответа 5s и делает один повтор

t=0.000  client    → orders     POST /orders {idempotency_key: none}
t=0.004  orders    → payments   POST /charge {order: 7714, amount: 1890}
t=0.005  payments  ⋯ acquirer   POST /v1/charge             [задержка 30s]
t=5.000  client    ✗ orders     таймаут клиента (5s), исход НЕИЗВЕСТЕН
...
ИТОГ: заказов 2, списаний 2, клиент заплатил 3780 вместо 1890 и на экране увидел ошибку
```

## Команды

```
./lab scene <id>            прогнать сцену и напечатать timeline
./lab scene <id> --explain  то же + пояснение, что именно смотреть
./lab scenes                список сцен текущего профиля
./lab state                 состояние данных: заказы, платежи, курьеры, уведомления

./lab up <профиль>          поднять профиль (сцена делает это сама)
./lab down                  остановить, тома оставить
./lab reset [профиль]       вернуть исходное состояние данных, тома пересоздать
./lab logs <сервис>         структурированный лог сервиса
./lab pull [профиль]        обновить образы
./lab build                 собрать образы локально, если GHCR недоступен
```

В `stdout` уходит только вывод сцены — его копируют в текст шага как есть.
Всё служебное идёт в `stderr`, поэтому `./lab scene 1 > timeline.txt` даёт
ровно артефакт и ничего лишнего.

## Что внутри

Профили Compose включаются по мере курса: студент никогда не поднимает всё
сразу — это и ресурсный потолок, и педагогика (в кадре только то, что уже
введено).

| Профиль | Модули | Что добавляет | RAM в покое |
|---|---|---|---|
| `mono` | m01 – m03 l04 | `monolith`, `postgres`, `acquirer` | ~40 МБ |
| `split` | m03 l05 – m04 | + `notifier`: уведомления уехали за сеть | ~50 МБ |
| `net` | m05, m12 | + `toxiproxy`: сеть можно рвать и замедлять | ~60 МБ |
| `broker` | m06–m07 | + `rabbitmq`, `kafka`, `courier`, `orders`, `outbox-relay` | ~1,0 ГБ |
| `cdc` | m07 l03 | + `debezium`: события из журнала репликации | ~1,6 ГБ |
| `cluster` | m08 | `kafka-1..3`, `postgres-replica`, `orders` (вместо `broker`) | ~1,3 ГБ |
| `cache` | m09 | `kafka`, `redis`, `orders` | ~1,1 ГБ |
| `scale` | m10 | `orders` ×2 и `balancer` перед ними | ~0,2 ГБ |
| `trace` | m11 | + `jaeger`: сквозной контекст запроса и приёмник трейсов | ~1,2 ГБ |
| `trust` | m13 | `gateway` перед `orders`: периметр, токены, контекст пользователя | ~65 МБ |

Профили следующих модулей добавляются вместе с ними и не ломают уже написанные
сцены. У m12 и m14 отдельных профилей нет намеренно: проверка гипотез ставится
на той же системе, защиты которой проверяет (сцены 35–36 на `net`), а изменение
системы добавляет порядок действий, а не машинерию — окно выката наблюдаемо там,
где инстансов и так два (сцена 39 на `scale`), а переезжает остаток монолита, и
остаток есть только там, где остальное уже уехало в свои службы (сцена 40 на
`broker`; сам брокер в ней не участвует).
**Профили не работают вместе**: при смене `lab` останавливает предыдущий —
в кадре только то, что уже введено.

- **`monolith`** — служба доставки одним процессом: заказ, оплата, назначение
  курьера и уведомление в одной транзакции. Та самая система, с которой курс
  начинается и об которую ломается.
- **`acquirer`** — внешний эквайринг. Задержка, исход и дедупликация по ключу
  идемпотентности задаются сценой; случайности внутри нет.
- **`notifier`**, **`courier`**, **`orders`**, **`outbox-relay`** — сервисы,
  которые появляются по мере распила монолита: уведомления за сетью, второй
  подписчик события, владелец заказов со своим исходящим ящиком и его
  отправитель.
- **`orders-2`** и **`balancer`** (профиль `scale`) — тот же сервис заказов,
  поднятый вторым экземпляром, и балансировщик перед ними. Точек входа у
  балансировщика две: 8080 — решение на каждом запросе (L7), 8081 — решение на
  каждом соединении (L4). Кто ответил, видно в заголовке `X-Lab-Instance`.
- **`jaeger`** (профиль `trace`) — приёмник и хранилище трейсов. Принимает
  OTLP, хранит в памяти, показывает деревья на <http://localhost:16686> —
  единственный порт стенда, который открывают в браузере. Спаны сервисы шлют
  сами: трассировка написана в `internal/lab/trace.go` без библиотек и
  включается непустым `LAB_OTLP_URL`, то есть только в этом профиле.
- **`gateway`** (профиль `trust`) — периметр перед службой: принимает токен,
  решает, пускать ли, и кладёт вниз по цепочке подписанный контекст
  пользователя. Проверяет двумя способами — на месте или вопросом эмитенту,
  с кэшем ответа. Эмитент токенов живёт в этом же контейнере отдельной ручкой:
  контейнер ради одной ручки объяснял бы устройство стенда вместо предмета.
- **`labctl`** — исполнитель сцен. Играет роль клиента (а в сценах m08 — ещё и
  оператора, отправителя и работника, в сценах m10 — шардов), собирает
  наблюдения сервисов и печатает timeline. Живёт ровно одну команду.

## Формат вывода и детерминизм

Сцена печатает **timeline двух сторон обмена** — главный артефакт курса.
Слева от стрелки тот, кто наблюдал событие; справа — вторая сторона.
`→` вызов, `←` ответ, `⋯` незавершённое ожидание, `✗` отказ или таймаут.
Последняя строка — итог обычными словами.

Вывод сцены обязан совпадать с текстом шага посимвольно, иначе сверять его
не с чем. Поэтому:

- **времена в timeline — сценарные**: прогон измеряет каждое событие
  по-настоящему, сверяет с допуском и печатает сценарное значение. Расхождение
  или пропавшее событие — блок `⚠ СЦЕНА РАЗОШЛАСЬ СО СЦЕНАРИЕМ` и ненулевой
  код возврата. Реальные измерения показывает `--explain`;
- **идентификаторы и итоги — настоящие**: номера заказов идут из
  последовательности базы, идентификаторы списаний — из журнала эквайринга,
  числа в `ИТОГ` считаются по данным. UUID в стенде нет нигде;
- задержки и отказы задаются **конфигурацией сцены**, а не случайностью.

Сцены, недетерминированные по своей природе (гонки, момент остановки),
помечаются в реестре и печатают предупреждение — шаг курса спрашивает про
класс исхода, а не про точные числа.

Подробности контракта с текстом курса — [`docs/CANON.md`](docs/CANON.md).

## Как устроен репозиторий

```
lab                     единственная команда стенда (bash + docker)
docker-compose.yml      профили по модулям курса
.env                    версия образов, пиннится полным тегом
scenes/registry.json    реестр сцен — данные, а не код
scenes/scripts/NN.json  сценарий сцены: расписание timeline и что печатать
scenes/expected/        эталонные выводы; смоук сверяет с ними посимвольно
services/               исходники образов курса
docs/CANON.md           имена, статусы и числа — контракт с текстом шагов
```

Новая сцена начинается с записи в `scenes/registry.json` и файла сценария
рядом; драйвер в `services/cmd/labctl` только производит события — весь текст
живёт в данных. Так каталог сцен и стенд не разъезжаются.

## Образы

Собираются в GitHub Actions и лежат в GHCR под полным тегом из `.env`
(`ghcr.io/kipyatl0/backend-architecture-lab/<сервис>:<версия>`), под linux/amd64
и linux/arm64. Локальная сборка — запасной путь: `./lab build`.

Сервисы написаны на Go — выбран за скорость старта и размер образа. Для курса
это деталь стенда: язык реализации студента не касается, в контенте не
упоминается и в примерах не всплывает. Студент не пишет код — он запускает
сцены и читает вывод.

## Требования

- Docker с поддержкой Compose v2 (`docker compose`), macOS · Linux · WSL.
- Профиль `mono` ограничен 0.9 ГБ и в покое занимает около 40 МБ. Потолок
  любого профиля курса — 4 ГБ: стенд живёт на ноутбуке.
- Начиная со сцен m08 исполнителю сцен пробрасывается сокет Docker
  (`/var/run/docker.sock`): предмет модуля — смерть узла, а у брокера и у базы
  нет ручки «умри», и остановить их можно только снаружи. Тем же сокетом сцены
  m10 перезапускают балансировщик, чтобы круг он раздавал с начала. Доступ есть
  только у `labctl` и только на время одной команды.
- Путь к репозиторию значения не имеет.
