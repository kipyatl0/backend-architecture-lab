Распределённая блокировка с истёкшей арендой
Назначением курьера занимается один работник — договорились через распределённую блокировку
Аренда берётся на 2 с; работа у первого работника застряла на 5 с

t=0.000  worker-1  → redis      SET lock:order:7714 NX PX 2с → взято
t=0.500  worker-2  ✗ redis      SET lock:order:7714 NX → занято  блокировка работает, как обещано
t=2.300  worker-2  → redis      SET lock:order:7714 NX → взято  аренда истекла сама, держателей стало двое
t=2.800  worker-2  → postgres   заказ 7714 → курьер Пётр
t=5.000  worker-1  → postgres   заказ 7714 → курьер Айгуль      он всё ещё считает себя держателем
t=7.000  worker-1  → redis      аренда взята, номер 1           прогон 2: у аренды появился номер
t=9.300  worker-2  → redis      аренда истекла и взята заново, номер 2
t=9.800  worker-2  → postgres   заказ 7714 → курьер Пётр, номер 2 → записано
t=12.000 worker-1  ✗ postgres   заказ 7714 → курьер Айгуль, номер 1 → отвергнуто хранилищем: 0 строк
ИТОГ: в обоих прогонах аренда истекла и держателей было двое; без номера в базе остался курьер Айгуль — от того, кто уже не имел права писать, с номером — Пётр

Распределённая блокировка — это аренда с истечением, а не замок. Держатель не узнаёт, что его сменили: между «у меня есть аренда» и «я пишу» лежит время, за которое аренда может кончиться.
Продлевать аренду в фоне помогает, но не решает: работник, у которого встал процесс или отобрали процессор, не продлит её и об этом не узнает. Гарантии «ровно один держатель» распределённая блокировка не даёт вообще.
Ограждающий номер переносит решение туда, где оно проверяемо: хранилище отвергает запись с устаревшим номером само. Работнику при этом ничего знать не надо — его запись просто не применяется.
Отсюда правило: блокировка нужна для эффективности (не делать работу дважды), а для корректности — условная запись. Если блокировка у тебя отвечает за корректность, у тебя её нет.
